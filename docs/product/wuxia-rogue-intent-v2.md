# 产品意图：武侠大地图 Roguelike（wuxia-rogue）— v2

## 0. 版本链

- **v1**：`docs/product/wuxia-rogue-intent-v1.md`（已验收，**只读，不修改**）。
- **v2（本文件）**：客户在体验 v1 后提出四项变更。v1 的 S1~S8、AC-1~AC-8 **继续有效**；v2 新增 S9~S13、AC-9~AC-13。
- **覆盖关系**：v1 中「升级自动成长」的获得方式由 v2 的「升级三选一」取代，但 v1 AC-5「升级带来可观察的成长」仍然成立；其余 v1 条款不变。
- 需求变更按应用要求走变更审批；本文件只表达产品意图与可验收边界，不写方案/名单/架构。

## 1. 客户原话记录

**v1 原始需求（2026-10-31）**：

> 「给我做一个武侠rouge 游戏吧，不要做成卡牌，要在一个大地图里面，自动攻击附近的怪物，然后收集掉落物，升级。如果运行好，后面应该满屏清怪的那种爽感。」

**v2 变更需求（2026-10-31）**：

> 「这个还是有问题的，首先怎么没有怎么开始游戏的介绍页面，其次也没有游戏结束的几分画面。其次升级怎么没有一个技能选择呢，开局应该可以选择几个门牌啊，还有就是游戏素材，应该用我电脑本地的 image2.5 模型来生成啊。」

**补充（客户）**：

> 「HF 缓存里有 Qwen-Image-2.1 这个模型」

## 2. 目标用户与场景（v2 增量）

- 新增玩家**首次进入的引导场景**：打开游戏先看到标题与玩法介绍，知道「要做什么、怎么操作、怎么变强」，再点开始。
- 新增玩家**一局结束的回顾场景**：死亡或通关后能看到完整战绩与评分，知道这局表现如何，并能立刻再来一局。
- 新增玩家**构建取舍场景**：开局选门派定基调，升级时在三个成长方向中做选择，形成「我这一局怎么变强」的决策感。
- 素材层面：美术不再只是程序化色块，而是本地模型生成的武侠题材素材，观感更完整、更可信。

## 3. 要解决的问题（v2 增量）

1. v1 缺少入口引导：玩家打开后不知从何开始、不知道玩法与操作 → 需要开始介绍页。
2. v1 缺少一局结束的反馈与总结：死亡/通关后直接结束，缺少战绩与评分 → 需要结算评分页。
3. v1 成长全自动、缺少决策：升级无选择，玩家没有「Build」感 → 需要升级三选一，且必须与卡牌明确区分。
4. v1 开局无差异：每局起点相同 → 需要开局门派选择，提供不同初始属性与专属成长方向。
5. v1 美术为程序化占位：观感与武侠题材不匹配 → 使用客户本机 Qwen-Image-2.1 生成素材替换，并保证运行时零依赖。

## 4. 范围（Scope）

### 4.1 继承 v1（继续有效）

- S1 大地图可移动探索；S2 自动攻击附近怪物；S3 怪物与击杀；S4 掉落与拾取；S5 成长（获得方式见 S12 调整）；S6 后期满屏清怪；S7 单局流程；S8 桌面端可运行原型。
- **明确不做卡牌**：不包含抽牌、出牌、手牌/牌组、卡牌构筑、回合制卡牌对战等任何卡牌机制。

### 4.2 v2 新增

- **S9 开始界面（标题/介绍页）**：进入游戏先看到独立开始页，包含游戏名、玩法说明（目标、操作方式、核心循环：击杀→掉落→拾取→升级）、醒目的「开始游戏」入口；不能只是一行小字或直接进入战斗。
- **S10 结算评分页**：一局结束（死亡或通关）后展示完整战绩：存活时间、等级、击杀数、拾取数、银两、最终攻击力；给出评分（如 S/A/B/C）；提供「再来一局」入口；结算数据与本局实际数值一致。
- **S11 开局门派选择**：开始游戏前从 3 个门派中选择（建议：剑宗偏攻速、刀门偏爆发、医谷偏生存/回复）；不同门派有可观察的初始属性差异与专属成长方向；选择结果影响本局。
- **S12 升级三选一（非卡牌）**：角色升级时弹出成长/技能选择面板，提供 3 个选项供玩家选择其一；选择后立即生效并影响后续战斗；替代 v1 的全自动成长；**不是抽牌/手牌/牌组/回合制**，样式可用卷轴/石碑等非卡牌表达。
- **S13 本地素材生成与替换**：使用客户本机 HF 缓存的 Qwen-Image-2.1 生成游戏美术（标题背景、角色、怪物、UI 素材等），替换程序化占位；生成物以 PNG/WebP 放入项目 `assets/` 并由游戏引用；运行时游戏不得联网、不得加载模型、不得依赖任何生成环境，仍可零依赖双击运行；未能生成成功的素材允许保留程序化占位并如实记录。

## 5. 验收标准（可判定）

> v1 的 **AC-1~AC-8 继续有效**（地图可移动、自动攻击、击杀掉落、拾取、升级成长、后期满屏清怪、非卡牌、可运行可复现）。以下为 v2 新增条款。
> **通用验收方式**：必须在真实浏览器/真实运行环境中人工目视验收，配合实际操作复现；仅凭截图、自述或日志不得判定通过。

- **AC-9 开始介绍页**
  判定：启动游戏后首先出现独立开始页，而非直接进入战斗；页面上可辨认地包含：①游戏名；②玩法说明（目标、操作方式、核心循环）；③醒目的「开始游戏」入口。点击「开始游戏」后进入门派选择/战斗流程。玩法说明不能只是一行小字（需构成可阅读的介绍区域）。

- **AC-10 结算评分页**
  判定：一局结束（死亡或通关）后自动进入结算页，无需玩家手动打开；页面上可辨认地展示：存活时间、等级、击杀数、拾取数、银两、最终攻击力，以及评分（S/A/B/C 之一）；存在「再来一局」入口且点击后能开启新一局。结算页上的各数值与本局过程中的实际统计一致（抽查至少等级、击杀数、存活时间三项对得上）。

- **AC-11 开局门派选择**
  判定：开始游戏后、进入战斗前，出现门派选择界面，至少 3 个门派可选（含剑宗、刀门、医谷或等价命名）；每个门派有说明其定位/初始属性/成长方向；选择不同门派进入游戏后，角色初始属性或成长表现存在可观察差异（例如攻速、攻击力、生命/回复中至少一项不同），且该差异可核对。

- **AC-12 升级三选一（非卡牌）**
  判定：角色升级时出现选择面板，恰好提供 3 个可辨识的成长/技能选项；玩家可选择其一，选择后效果立即生效，并可在后续战斗/属性中观察到变化（例如攻击范围、伤害、攻速、生命等）；下一次升级再次提供 3 个选项；面板在未选择前不自动替玩家选择（或明确可暂停选择）。
  **非卡牌判定口径**（必须同时满足）：
  1. 不存在抽牌、牌堆、手牌区、弃牌堆、牌组构筑、卡牌收集等元素；
  2. 选项在升级时即时出现，选择后即消耗/消失，不跨局收集、不进入卡组；
  3. 不存在回合制卡牌对战；战斗仍是即时自动攻击 + 走位的 v1 模式；
  4. 视觉表达采用卷轴/石碑/技能光球等非卡牌样式即可，不必是卡牌。

- **AC-13 本地素材替换且运行时零依赖**
  判定：①游戏运行中展示的标题背景、角色、怪物及主要 UI 素材为 Qwen-Image-2.1 生成的美术文件，而非纯程序化色块/占位（允许少量元素保留占位，但必须如实记录）；②生成物以 PNG/WebP 形式存在于项目 `assets/` 内并被游戏实际引用，可在目录与文件中核对；③断网状态下启动并游玩，游戏正常运行，不加载模型、不访问网络、不依赖 Python/生成环境；④素材生成记录可核对（哪些素材由 Qwen-Image-2.1 生成、哪些失败后保留占位），不得虚报成功；⑤在真实浏览器中目视确认替换后的观感与 v1 占位有可辨识的差异。

## 6. 非目标（Non-Goals）

- **不做卡牌**：抽牌/出牌/手牌/牌组/卡牌构筑/回合制卡牌对战一律不做；升级三选一是即时成长选择，不是卡牌。
- 不做联机/多人、排行榜、账号、云存档。
- 不做商业化、内购、广告。
- 不做完整剧情、任务线、长期 meta 养成。
- 不做移动端/主机端、手柄深度适配。
- 不规定门派具体数值、技能具体设计、美术风格细目（由策划/美术环节确定）。
- 运行时不得联网，不得加载/推理模型，不得把生成环境打包进游戏运行链路。

## 7. 约束（Constraints）

- **平台与运行**：桌面端单机原型，在真实浏览器中可双击/本地打开运行；引擎/技术栈仍由策划阶段决定。
- **素材来源（已核实环境事实）**：
  - 模型：本机 HF 缓存 `C:\Users\51054\.cache\huggingface\hub\models--Qwen--Qwen-Image-2.1`（snapshot `d26bb612…`，diffusers 管线 `QwenImage21Pipeline`；transformer ≈14.2GB、text_encoder ≈17.5GB、VAE 另计）。
  - 另一本地拷贝 `C:\Users\51054\ai-models\qwen-image-2.1` 仅配置与未完成下载，**权重以 HF 缓存为准**。
  - 硬件：RTX 4090 24GB；Python 3.12.10；当前未安装 torch/diffusers/transformers/accelerate，需一次性安装（PyPI 可访问），生成可离线。
  - 24GB 显存装不下全部组件，生成需 device_map/CPU offload，单图可能分钟级。
- **失败处理**：若某个素材生成失败，允许保留程序化占位并**如实记录**，不得虚报已生成；不得用占位冒充生成素材。
- **运行零依赖**：生成脚本与输出放在项目内由后续素材属主管理；游戏运行时不得联网、不得加载模型、不得要求 Python 环境。
- **非卡牌边界**：任何新增选择/面板都必须满足 AC-12 的非卡牌判定口径；需求变更必须走新版本意图（v3…），不原地修改 v1/v2。
- **验收方式**：AC-9~AC-13 需真实浏览器目视验收，不接受截图造假或口头自述。

## 8. 质量档位

- 仍为**可玩原型（Prototype）**，但本版要求「体验闭环完整」：开始→选择→战斗→成长选择→结算→再来一局的路径必须走得通、看得懂。
- 美术以「本地模型生成、观感明显优于程序化占位」为准，不要求商业级精度与统一风格；允许个别素材保留占位但须如实标注。

## 9. 本环节不产出

策划方案、门派/技能的数值设计、UI 布局稿、生成脚本实现、技术架构、人员名单与排期——均属后续环节。
